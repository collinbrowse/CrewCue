# Merge Concurrency Policy

**Audience:** engineers and AI coding agents implementing offline-capable mutations.  
**Intent:** define the MVP rules for overlapping updates when clients go offline and later reconnect.

**Related:** [MVP delivery chunks and cloud strategy](./mvp-delivery-chunks-and-cloud-strategy.md) · [ADR 0003](../adr/0003-canonical-data-and-event-log.md)

---

## 1. Strategy per entity

This MVP policy covers the entities most likely to receive overlapping offline writes first: athlete pings, race room state, tasks, and protocol notes. If new mutable entities such as plan versions or incidents gain offline mutation support, extend this policy before shipping that behavior.

### Athlete pings

- **Strategy:** append-only.
- Every accepted ping is stored as its own event/row. We do **not** discard older pings just because a newer one arrives later.
- The derived "`latest` ping" pointer uses **last-writer-wins** based on **server-received timestamp** so read models can answer "what is the athlete's most recent ping now?"
- If two delayed pings arrive out of order, both remain in history; only the derived latest pointer changes.

### Race room state (`name`, `status`)

- **Strategy:** last-writer-wins (LWW).
- The server chooses the winner using the **server-received timestamp**, not the client clock.
- These fields are treated as current state fields where the MVP benefit of deterministic overwrite is higher than the cost of prompting humans to merge text.
- Prior values are still preserved in the event log so operators can inspect what happened if a reconnecting client overwrites a newer state unexpectedly.

### Tasks

- **Strategy:** LWW for status, explicit handling for assignment conflicts.
- Task status changes such as `open`, `in_progress`, and `done` use **LWW by server-received timestamp**.
- Assignment changes must **not** be silently merged when concurrent clients pick different assignees.
- For assignment mutations, the server should either:
  1. accept the change only when the client's expected task version or current assignee still matches, or
  2. reject the mutation with a conflict response so the client refreshes and retries with current state.
- This keeps simple status updates lightweight while preventing ambiguous "two people were assigned at once" outcomes.

### Protocol notes

- **Strategy:** append-only.
- New notes are stored as separate events/rows and remain visible in the timeline.
- If the product later needs editable notes, treat edits as new revision events rather than destructive in-place replacement.
- For the MVP, the safest rule is that note creation never overwrites another note.

---

## 2. Client responsibility

- Every mutation must include an **idempotency key** generated by the client as a **UUID**.
- The client must generate the key **once per user intent** and reuse that same key for retries caused by offline replay, timeouts, or uncertain network outcomes.
- The server must treat duplicate deliveries with the same idempotency key as the **same mutation**, returning the existing result instead of applying the mutation again.
- This is required for all mutation types, including append-only writes, because reconnect flows commonly replay requests.

---

## 3. Conflict resolution

For the MVP, we favor **LWW** where the entity already has a natural "current value" because it is simple, deterministic, and easy to implement across mobile reconnect paths. That keeps the first offline-capable client behavior understandable without blocking on richer merge UX, per-field vector clocks, or collaborative editing semantics.

We still keep the **append-only event log** because "simple winner selection" is not the same as "perfect truth." The event log preserves overwritten attempts, supports audit trails, and gives operators a path for manual resolution when a late-arriving offline write should be reviewed instead of blindly trusted. In other words: **LWW decides the live projection for MVP speed, while the event log preserves enough history to debug, audit, and recover.**
