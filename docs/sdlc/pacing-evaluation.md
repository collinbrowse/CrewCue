# Pacing model evaluation

How to measure whether the pacing model (`services/api/src/lib/pacingEstimate/microModel`) predicts aid arrivals and finish times well, and how to keep it from getting worse.

Supersedes the interactive GPX backtest proposed in #498 / #499. Its GPX split extraction lives on as the non-interactive `pacing:eval:import`.

## Commands

| Command | What it does |
| --- | --- |
| `npm run pacing:eval -w @crewcue/api` | Scores every predictor on every corpus effort and prints tables for all, tune, and holdout |
| `… -- --split holdout` | Prints one split only |
| `… -- --markdown` | Prints the same tables as Markdown, for PR bodies |
| `… -- --detail` | Adds per-effort finish error for the micro-model |
| `… -- --json` | Writes the full result, every checkpoint and segment, for ad-hoc analysis |
| `… -- --check` | Runs the accuracy gate against `fixtures/pacing/eval/metrics-baseline.json` (exits 1 on change) |
| `… -- --write-baseline` | Re-records the gate after an intended model or corpus change |
| `npm run pacing:eval:import -w @crewcue/api -- --help` | Adds a real completed effort from GPX files |
| `npm run pacing:eval:synth -w @crewcue/api` | Regenerates the synthetic part of the corpus |

Everything is deterministic and offline. The gate also runs in `npm run test -w @crewcue/api`, in `evaluate.test.ts`, so CI enforces it.

## Why a corpus harness instead of an interactive tool

A pacing model is good when it is accurate across many athletes, courses, and distances. One race checked by hand does not tell you that. The interactive CLI answered "how did this one race go?" It produced no aggregate, no comparison against simpler models, and no protection against overfitting. Nothing stopped a later change from undoing a gain.

The harness answers four questions:

1. **Accuracy.** For finish and checkpoints it reports MAPE, signed bias, MAE in minutes, and the share of predictions within 5% / 10% (finish) or 15 / 30 min (checkpoints). Percent error is the primary metric because the corpus mixes marathons and 100-milers.
2. **Level vs shape.** Shape error rescales each prediction so its finish matches the actual finish. A wrong level means fitness or endurance is off (C1/C2). A wrong shape means terrain or fatigue is off (M(g), C3).
3. **Where the error lives.** Aid-to-aid segments are bucketed by terrain (flat, rolling, climbing, descending) and by race third (early, middle, late).
4. **Whether it earns its complexity.** Every metric is also reported for three baselines:
   - even pace: the legacy deterministic estimator;
   - Riegel 1.06 with no terrain;
   - the app default: 6:00/km plus the climb heuristic, which racers saw before estimates were attached.

The interactive mode was dropped. Re-running `pacing:eval` after an import gives the same per-race view (`--detail`) plus everything above.

## Corpus

`fixtures/pacing/eval/` holds `efforts/<id>.json`, one per completed effort, and `courses/*.gpx`.

An effort file records:
- the course;
- `raceStartAt`;
- the summary history the athlete had before the race (what the app would have seen);
- the actual moving elapsed at each checkpoint, finish included. Aid dwell is excluded so pace error is not mixed with station time; PR D models dwell separately.

### Tune and holdout

Each effort's split comes from a salted hash of its `group` (one athlete). The split is never stored, so nobody can pick which side an effort lands on, and one athlete is never on both sides. About 30% of athletes are held out.

The rule is to tune constants against `--split tune` only, then report `--split holdout` before and after in the PR. A change that improves tune but not holdout is overfitting.

### Provenance

`provenance.kind` is required and limited to three values:

| Kind | Allowed when |
| --- | --- |
| `own-effort` | Your own race, or one you have explicit consent to use. Requires `contributor` and `consent`. |
| `public` | The data is public domain or licensed for redistribution (CC0, CC BY, ODbL…). Requires `source` and `license`. |
| `synthetic` | Generated by `evaluation/synthetic.ts`. Never evidence of real-world accuracy. |

Never add scraped personal data, such as other people's Strava activities or per-runner results scraped from timing sites.

Only derived numbers enter the corpus: split seconds and history summaries. The import never stores the raw race or training tracks.

### What is in it today: synthetic only

There is no openly licensed corpus of timed ultra efforts paired with the runner's own pre-race history. Without the history, the level part of the model cannot be evaluated at all. The search turned up these candidates:

- **Open GPS tracker exports.** The closest openly licensed match was a CC0 city-marathon tracker export (Ulm open data). It is a road marathon with no paired history.
- **Per-runner race results.** Personal data.
- **Knechtle et al. 2025, Western States 2006–2023 pacing (Scientific Reports).** Aggregate per-segment speeds. It is CC BY-NC-ND, which is not redistributable in a derived fixture, and it has no history either.

The first real efforts should be the owner's own completed races, imported with `pacing:eval:import`.

Until then the corpus is 60 **synthetic** efforts: 10 athletes × 6 courses, from a trail marathon to a mountain 100-miler. The 50k uses the existing fixture course.

To avoid grading the model against itself, the synthetic truth is a different model:
- Minetti (2002) cost polynomial instead of the production quadratics;
- power hiking above a per-athlete grade, at Tobler speed;
- a downhill gain cap eroded by cumulative descent, with a technical-descent penalty;
- a per-athlete Riegel exponent of 1.06–1.18;
- fade, altitude sensitivity from 1200 m, day form, and per-km noise;
- history with GPS distance and gain error and stop time inside elapsed.

Synthetic numbers show the harness works and catch regressions. They say nothing about how accurate the model is for real racers. The report and every synthetic file say so.

## Adding a real effort

```bash
npm run pacing:eval:import -w @crewcue/api -- --id tmr-100k-2026 --group athlete-collin --course ~/races/tmr-course.gpx --race ~/races/tmr-recording.gpx --training ~/runs/long1.gpx --training ~/runs/long2.gpx --contributor "Collin Browse" --consent "own data"
```

- **Course GPX:** the planned course with aid waypoints. It is copied into `courses/<id>.gpx`.
- **Race GPX:** your timed recording.
  - The import finds the first arrival within 75 m of each checkpoint, in course order.
  - Time spent within 75 m of a checkpoint while slower than 30 min/mi counts as stoppage and is excluded.
  - It fails clearly if timestamps are missing or a checkpoint is never reached.
- **History:**
  - Pass timed training GPX files with `--training`, and/or summary rows recorded before the race with `--history-json`, for example a Strava export of the runs the app would have seen.
  - Rows recorded after the race start are rejected.

Then review `npm run pacing:eval -w @crewcue/api -- --detail`. Re-record the gate with `-- --write-baseline` and commit the effort, course, and baseline together.

## Changing the model or its constants

1. Run `npm run pacing:eval -w @crewcue/api -- --markdown` before the change. Save the output.
2. Make the change. Tune against `--split tune` only.
3. `npm run test -w @crewcue/api` fails the accuracy gate, which is expected, and lists every gated metric that moved.
4. Run `-- --write-baseline` and paste before/after holdout tables into the PR.

The gate fails on any change larger than 0.05 percentage points in either direction. A worse result needs a justification. A better one has to be locked in so a later change cannot quietly give it back.

Gated metrics (micro-model only; all, tune, and holdout):
- finish MAPE;
- |finish bias|;
- checkpoint MAPE;
- shape MAPE.

Baselines are reported but not gated.

**Do not tune constants on synthetic efforts.** That fits the synthetic truth model, not runners. `CONSTANTS_FOR_APPROVAL.md` stays provisional until real efforts exist.

## Code map

| Path | Role |
| --- | --- |
| `services/api/src/lib/pacingEstimate/evaluation/corpus.ts` | Effort schema, validation, loader, tune/holdout assignment, fingerprint |

| `services/api/scripts/pacing-eval*.ts` | CLIs |

`npm run pacing:backtest` and `backtest.ts` stay as the single-scenario view that the micro-model predictor reuses.
